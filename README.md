## 🛑 Дисклеймер для тимлидов и архитекторов

Этот проект — манифест против **«Java в синтаксисе Kotlin»** и бездумного карго-культа: например, попыток реализовывать сложную и запутанную бизнес-логику на Go только потому, что «так проще».

Если вы считаете, что Kotlin можно освоить за две недели, а хороший код сводится к `var`, `!!` и бесконечным классам-утилитам, этот репозиторий вам, скорее всего, не понравится.

Здесь Kotlin рассматривается не как новый синтаксис для привычного Java-кода, а как инструмент для построения выразительной модели предметной области, явных архитектурных границ и защищённых инвариантов.

Если в вашей команде качество модели, чистота кода и архитектурные инварианты важнее скорости производства временных решений и кода с тяжёлым Java-акцентом — мы, вероятно, сработаемся.

В противном случае давайте сэкономим время друг друга.

## 🏗 Архитектура приложения

В проекте используется **Clean Architecture с модульной структурой**.

- бизнес-правила предметной области (инварианты) не зависят от фреймворков и инфраструктуры;
- зависимости направлены от внешних слоев к внутренним;
- взаимодействие с внешним миром осуществляется через порты и адаптеры.

Архитектурные границы **обеспечиваются на уровне Gradle-модулей**.

### Структура модулей

* `:domain` — ядро системы (бизнес-логика, инварианты). Не имеет внешних зависимостей.
* `:application` — сценарии использования (Use Cases), входящие и исходящие порты.
* `:infrastructure` — реализация исходящих адаптеров (БД, Kafka, gRPC, внешние API).
* `:api` — входящие адаптеры для клиентов и внешних систем.
* `:bootstrap` — конфигурация DI и точка запуска приложения.
* `:common` — переиспользуемые типы и контракты.
* `:tests` — интеграционные и модульные тесты архитектурных слоёв.

> **Пример правила зависимостей:** модуль `:application` может зависеть только от домена и общих типов:

```kotlin
dependencies {
    implementation(project(":common:types"))
    implementation(project(":domain"))
}
```

## Реализованные паттерны и решения

### Событийно-ориентированная архитектура (EDA)
* **Внутреннее взаимодействие:** Реализовано на доменных событиях (**Domain Events**) для асинхронной координации и связи между ключевыми агрегатами `Order` (Заказ) и `Courier` (Курьер).
* **Внешняя интеграция:** Интеграционные события отправляются во внешние системы строго в рамках контрактов **Protobuf** сторонних сервисов.

### Тактические паттерны DDD
* **Aggregate / Entity / Value Object** — инкапсуляция бизнес-логики и обеспечение целостности данных.
* **Domain Service** — логика предметной области, не принадлежащая конкретному агрегату.

### Архитектурные паттерны
* **Outbox Pattern + Debezium (CDC)** — гарантированная доставка событий в Kafka по принципу *at least once*.
* **Command-Query Separation (CQS)** — четкое разделение операций чтения и записи данных, для исключения избыточной загрузки тяжелых агрегатов.
* **Unit of Work** — обеспечивает строгую согласованность в рамках одного бизнес-сценария.
